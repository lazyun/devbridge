领域和任务都是 Core 中的持久对象。提案、消息已发送、用户确认、运行结束和验收完成是不同事实，界面不得互相替代。ChatGPT 会话只展示一个统一右侧面板，正式确认、运行权限、结果与历史均在面板中处理。普通对话入口保留。

WebUI 的执行历史以任务标题和各次冻结执行目标展示，执行 ID 保留在详情。GPT 面板 v40 在任务标题下显示当前续作的类型与目标；尚未准备新方案时显示待准备状态，不把旧目标作为当前工作。详见 [续作显示验证](../validation/continuation-display-2026-10-25.md)。

1. 用户在创建确认单选择 GPT 审查、Codex 审查或不审查。GPT 审查直接读取正式授权范围并提交报告；Codex 审查正常输出原生结果，随后由 GPT 分析并提交。不得要求 Codex 为 Core 输出工程判决 JSON。
2. `APPROVAL_READY` 新方案在发布前检查验证规格是否可执行。必需命令检查必须有确定性执行路径；必需 CUSTOM 指令保留为逐项分析义务，不能伪造 Bridge 观测。拒绝发布不会终止审查，作者可以在原 Review 中修正后提交。历史报告仍可读取和回放；旧方案的审批资格仍检查可执行性。
3. 用户批准 `APPROVE_AND_START` 后，Core 持久化冻结配置并启动实施，不再增加同内容的启动确认。GPT 文件实施沿准确文件权限继续。不审查路径使用 `CONFIRM_AND_START_IMPLEMENTATION`，一次正式确认完整实施、验证方案与明确选择的后端、模型和运行配置，冻结准确版本后立即启动。创建任务本身仍不启动实施。历史 `CONFIRM_IMPLEMENTATION` 继续只冻结定义，其后可用 `START_APPROVED`，旧回执不会被赋予新的启动权限。
4. 实施结束后进入验证，验证证据由实际运行与 Git 观测提供，GPT 负责逐项分析。Codex 成功退出不能替代工程验收。
5. 验证后提供延续任务、完成并合入、暂存任务。延续保留原 Task 并按当前资格修订或重验；暂存保存进度与剩余工作；完成的正式确认冻结逐仓提交及合入计划，所有目标合入成功后才完成 Task。旧 ACCEPT 接口仅兼容历史验收语义，不表示已合入。完成合入在副作用前被明确拒绝且原计划可安全释放时，用户可释放原计划，再以 MERGE_FEATURE_AREA 和准确 featureArea.completionTaskId 正式确认一个绑定原任务的后继合入计划。Core 冻结新的开发分支目标；原验收、原完成计划及已完成成员回执保持不变，所有新目标合入后才完成原任务。旧格式的合入操作继续使用其原始载荷、hash 与回执，不能因新增字段改变身份。

面板只把已结束、被替代、过期或失效的操作放入不可确认的历史。PARTIAL / UNKNOWN 留在后续操作，先回读原请求；仅 Core 返回 `canResume` 才可继续同一次请求。不得盲目重发未知提交。

临时读取失败保留上次卡片及输入，显示过期提示并暂停提交；成功读取后恢复准确资格。读取采用有上限的失败退避。当前 Task 未决操作和用户准确创建请求在 Session 列表截断前优先；列表不完整时明确提示。其他创建提案需用户显式选择，选择本身不创建对象。

GPT 自动交接只来自准确、已消费且步骤完成的用户确认或明确重新授权回执。待交接目标在读取失败时保留，恢复宿主展示快照后须先回读准确正式回执。发送前先保存带准确目标与原请求内容的交接日志，等待异步宿主保存确认；保存失败时显示尚未发送并允许显式重试。刷新把未完成发送恢复为 UNKNOWN，禁止自动重发。消息送达与业务回执分开：准确 requestId 的准备 intent、原 Review/Run 的正式报告、原 Run 的 RECORDED 分析或原 Task/版本/workflow 的文件结果，才确认对应产物已入库；消息 ACK 不代表这些业务产物完成。重试前重新核对当前目标、资格、原文及请求身份，由用户显式点击，保留原 prepare requestId；不自动审批、启动或重放未知业务写入。准备失败可由用户在面板使用原 requestId 再次请求准备，不能变成自动审批。准备请求按完整 action/target 身份区分；同一定义下 Execution、Decision 或其他权属字段变化时使用新 requestId，仅原准确操作的重试沿用旧 ID。

面板 v41 在宿主声明 `openai/message` 能力时，显式向当前主对话发送消息（`target=active, send=true`）；兼容发送入口开启滚动到回答。宿主接收后请求返回 inline 主对话，发送未知或拒绝时保留面板，不切换传输重发。交接日志记录发送路径，但不能据此宣称 GPT 回答已持久保存。普通主输入框回复在当前宿主刷新后同样出现「无法加载此回复」，因此刷新恢复与卡片消息形成独立轮次的端到端验收仍未通过。详见 [消息路由修复与宿主复现](../validation/card-conversation-routing-2026-10-25.md)。

面板 v42 / 确认单 v12 为未确定提交提供「核对并撤回原请求」：先只读核对准确回执，再由 Core 通过与消费相同的写入事务边界记录未消费拒绝，封存原 requestId。若消费已经生效，只返回原事实；不撤销业务结果、不启动步骤。迟到的相同提交读取封存回执；变更载荷拒绝。只有准确、持久的未消费回执才能恢复编辑，用户仍须重新确认。读取失败、撤回响应丢失或原载荷不完整继续保持未知，不根据查无记录直接解锁。旧 v11 未知快照保留完整请求；外层仅将相应待确认行展示为「结果待核对」，不改 Core 状态。见 [安全恢复验证](../validation/confirmation-submission-withdrawal-2026-10-25.md)。

CONTINUE_TASK 确认完成后，面板核对准确 RECORD_TASK_CHOICE 回执和当前 Task/Execution/定义，再向原 GPT 请求准备后续方案。保留已有结果和未提交变更，不重复要求延续确认，也不直接启动 Run。界面明确展示「已确认延续」和后续方案的准备状态；原范围内的实施修正可使用当前 REQUEST_CHANGES 资格，定义不变的证据重跑使用 REQUEST_REVERIFICATION，需要工程补审时才请求补审。新方案仍需用户在面板正式确认。部署前已结束的延续确认不由历史读取自动触发，可使用「准备后续方案」显式续接。修复证据见 [延续交接修复](../validation/task-continuation-repair-2026-10-24.md)。

当前审查状态和历史运行证据分开：准确重新授权证明可以取代旧重启分类的可操作性，但保留历史 UNKNOWN 事实。独立 UNKNOWN / CONFLICT、取消、孤儿运行和未完成 finalization 继续按原守卫处理。

不审查单次确认的实现与回归证据见 [修复记录](../validation/unreviewed-single-confirmation-2026-10-24.md)。

## Task 当前待操作链路

已部署 `.77`，对应 schema 134、task-panel-v44、确认单 v13。修复及验证记录见 [Task 唯一链路修复](../validation/task-single-action-chain-repair-2026-10-25.md)。

schema134 按准确原回执归并历史冲突：已正式接续同补审请求的旧深度拒绝可退出占用，但 PARTIAL 历史不改写；已过代际的未消费提案继续被封住，真实 UNKNOWN 仍保留。只有多个真实活动候选才需要用户选择，唯一剩余链路不再被历史记录阻塞。原任务恢复与真实 GPT 面板验证见 [历史占用恢复](../validation/task-action-history-recovery-2026-10-25.md)。

每个 Task 在 Core 持久化一个当前操作头及单调递增的 generation。GPT 提案在准备事务中占据该头，提交时在同一写事务比较准确 intent 与代际；WebUI 新命令携带读取时的 taskActionGeneration，并在业务写事务内比较。普通准备、显式替换和跨 Session 请求使用同一任务头。创建前仍按原创建请求幂等，创建 Task 的事务将新任务原子绑定到已消费的创建父请求。

未提交方案可以显式放弃，Core 将其封存为 SUPERSEDED，并拒绝迟到提交。已经消费的 PARTIAL / UNKNOWN 持续占据原链路，必须核对准确业务回执或按 Core 提供的原步骤恢复；放弃提案不能撤销已消费结果。正式恢复确认已记账但后继尚未消费时仍占据任务头，历史已失去当前恢复代际或链接的回执不能阻塞新一代消费。已完成请求优先按准确不可变回执回放，不受当前代际变化影响。

任务阶段、状态、当前定义/Review/Execution、当前运行状态、分析入库及延续/暂存等决策事实会推进代际。旧代际的新提交拒绝，不按同 Task、同阶段或同定义推定仍有效。原生权限请求和运行完成回调属于原运行链路，仍使用准确 Run 的既有身份、权限和结果守卫。准确取消当前 Run 属于该原链路的终止控制，继续由原取消合同核对身份和副作用；不能启动新 Run。

GPT 面板与 WebUI 读取同一个 taskView.actionNode；占用时收起或禁用其他独立入口，显示原链路的等待原因。其他 Session 只能看到安全状态摘要，不获得原 Session、请求正文或 intentId。旧多提案迁移不按时间挑选：进入 CONFLICT 后，用户只能显式保留自己有权读取的一条链路、关闭其他未提交提案。另有已消费未明链路时不能丢弃它，多个未知副作用需继续核对原回执。迁移保留冻结 JSON、原请求及历史，不自动确认或派发。

确定无法通过深度门禁的历史补审启动，以及正式采纳后派发前取消的原执行，可按准确 Core 证据沿原任务转入新的正式启动或停止修订。释放占用写入不可变回执，原审批和部分步骤不被改写为成功。

验证运行结束后，分析、延续和暂存是当前决策节点允许的分流；延续或暂存不表示验证通过。完成并合入仍需全部必需验证及原逐仓合入门禁。选择任何分流后推进代际，旧按钮和旧提案不能改变后来的决定。

## 工程执行边界

Core 在派发前负责正式授权、身份绑定、冻结方案、工作区和运行权限。派发给 Codex 的工程指令不包含流程身份或查找确认回执的要求。GPT 继续负责工作流决策及对原生执行结果的分析。

Bridge 托管的 Codex 子进程关闭 Apps、插件及 MCP 自动安装；每次新建或续接工程会话时，按准确工作区读取有效配置，逐项禁用继承的 MCP 服务，并在派发前核对该会话的实际工具清单。配置或清单无法核实时停止新派发。原生文件、命令工具及按运行身份绑定的窄范围工程工具保持可用；Core 的只读、写入范围和运行权限审批守卫仍生效。此设置不改用户个人 Desktop/CLI 配置。

授权不依赖 Codex 再次查找 Core 回执。运行时职责说明独立于已批准工程指令，后者逐字保留。旧活动 Turn 可以只读观察或重新连接，不为加载新策略重启；同一旧会话开始新的 Turn 前必须应用并核对新边界。历史工具内容不会从既有会话记录中被抹除。

`.71` 对每个新原生 Turn 发送当前阶段的开发者策略，明确替换持久或压缩历史中的宿主阶段角色限制。实施策略列出原冻结写入 grants，验证策略继续保持产品源码只读；原批准指令逐字保留，原模型和推理配置固定，缺少冻结模型时在派发前拒绝。此说明不扩大原生沙箱权限，旧 Run 不因部署自动重跑。原生同 Thread 阶段切换和实际拒写证据见 [轮次策略修复](../validation/codex-turn-policy-2026-10-25.md)。

实施 SCOPE_CONFLICT 先停止并进入正式恢复核对，保留改动和原始结果。范围不变且已核验的部分成果可沿准确资格同版本续作；
范围变化使用 REVISION_REQUIRED 绑定的 RECOVERY_PURPOSE 正式确认新方案，不等于自动重审。
确需补充工程判断时，仅按 Core 提供的同任务补审资格发起；冲突或证据不足不能靠重试、补审或新任务绕过。
详见 [范围冲突分流合同](engineering-scope-responsibility.md#implementation-scope_conflict-handling)。

F6 通用 GPT 交接的残留修复见 [交接日志与业务回执](../validation/gpt-handoff-receipts-2026-10-24.md)。日志是宿主展示快照，不替代 Core 授权或业务回执；恢复的完成声明须经新鲜只读事实重新核对。

统一工作台在请求 GPT 回答后保持 PiP/fullscreen 展示，消息仍路由到当前主对话；不会为显示回答主动关闭工作台。手动关闭后可显式重新打开，不重发上一次请求。修复和宿主加载限制见 [工作台保持验证](../validation/panel-message-preservation-2026-10-25.md)。


Codex 后继实施运行保留原生 Thread 时，在全新 Turn 启动前以 `thread/inject_items` 追加当前宿主 developer 策略，使其在持久历史和模型输入中晚于旧验证角色。每次策略继续依据准确冻结 TaskPermissions；不修改原工程 Prompt、权限、模型或历史。策略注入失败则拒绝启动，已运行 Turn 的重连不注入、不重放。见 [实施角色通道验证](../validation/codex-implementation-role-channel-2026-10-26.md)。
