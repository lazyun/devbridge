# GPT 统一工作面板

进入 Dev Bridge 后，在同一会话使用一个面板。宿主支持 PiP 时请求悬浮展示；不支持 PiP 的客户端保留同一个面板的内嵌布局。改变任务阶段不会产生新的会话卡片。

面板顶部只保留当前项目、领域、任务类型与名称、阶段、执行方式及总进度。领域和任务通过“切换领域与任务”显式选择；浏览不替 GPT 选择业务操作目标。

## 三个页签

- **后续操作**：当前待确认表单、运行问题、GPT 审查/分析/文件实施请求，以及 Core 当前允许的操作。“＋ 发起操作”可填写需求、新建领域/独立任务、配置当前项目与开发分支。
- **结果与报告**：审查报告、实施与验证结果、GPT 正式分析和任务要求。完整记录按准确操作读取，长内容可以展开；不需要返回会话寻找报告。
- **历史操作**：保留原方案、状态和回执，只能读取、刷新，不能重新确认或续接。

## 流程入口

| 阶段 | 面板内处理 |
| --- | --- |
| 项目与分支 | 填写或请求选择已登记项目、逐仓开发分支；在正式表单确认 |
| 创建领域/任务 | 填写需求，由 GPT 静默准备；正式表单明确区分领域和任务，选择 GPT 审查、Codex 审查或跳过审查 |
| GPT 审查 | 请求实际读取授权文件并提交审查结果；授权过期时在本面板核对原授权版本并由用户重新授权 |
| Codex/Pi 审查 | 查看执行状态；运行结束且 Core 要求分析时，请求 GPT 分析实际输出并正式提交 |
| 审批与修订 | 在面板填写修改意见或请求审批；正式确认、模型和思考等级选择均留在同一面板 |
| Codex 实施/验证 | 查看原始问题和原始选项，不预选答案；核对最终回答后直接提交 Core 的 UserDecision 合同。权限请求先读取完整原文，再提交准确选择 |
| GPT 文件实施 | 仅在准确、有效的获批文件权限下请求继续实施，结果按原合同提交；后续 Codex 验证仍沿用获批验证方案 |
| 结果分析 | 读取准确 Run 的证据、报告格式和 sourceHash，由 GPT 提交正式分析，不要求 Codex 为输出格式重新执行 |
| 验证后的处理 | 延续原任务、完成并合入、暂存任务；完成仍以 Core 的验收、提交与逐仓合入回执为准 |
| 恢复、取消与重试 | 仅展示 Core 当前资格，重新核对准确目标；未知结果不自动重发，不用新任务替换旧任务 |
| 已结束 | 查看结果或显式发起独立新工作，不重新打开已结束任务 |

当阶段为 **GPT 审查待重新授权** 时，“后续操作”只展示授权失效的原因和“重新授权并继续 GPT 审查”按钮。点击一次后，面板核对 Core 当前授权版本并提交；成功回读原 Review/Run 后，自动请求 GPT 在原会话继续审查并提交报告，无需再次输入“继续”。此时不提供其他任务操作或新建入口。宿主明确拒绝调用时可在同一按钮重试；请求是否受理未知时保留原请求，不自动重发。结果与历史页签始终可查看。

正式确认已完整成功且新鲜回读身份一致时，GPT 审查启动和已授权 GPT 文件实施会自动续接到原会话；部分成功、未知或历史回执不会触发续接。Codex 实施仍由已批准的 Core 流程启动。

“交给 GPT 准备”只发送用户填写的需求，不等于业务操作已经完成。GPT 使用现有会话静默准备，面板会自动读取新表单；新建提案按本次固定 prepare requestId 关联，旧创建提案不会成为当前任务的必经步骤。

Codex 运行问题的最终回答直接经 Core 校验和与提交接口处理，不交给 GPT 改写。保密回答只存在当前面板内存中，不写入组件持久状态或转交 GPT。回答是否被后端接收未知时保留准确状态，只提供 Core 允许的等待或取消路径，不自动重发。

操作可用性来自 Core。面板不授权扩大范围、不降低必需检查，也不把运行成功、报告主张或请求受理当成验收成功。

## 自动刷新

面板会继续读取最新任务状态，同时保留当前页签、已展开的报告、滚动位置和未提交的编辑草稿。主动收起的确认项不会在每次刷新后重新打开。使用下拉菜单或选择报告文字时暂缓绘制，结束操作后补上最新内容。

这些只属于当前任务定义下的展示状态。切换任务或任务定义变化时重新核对，已失效的确认会立即禁用；保持展开不代表确认仍然有效。

## 原会话显示旧面板时

旧工具结果仍可能被 ChatGPT 的右侧查看器恢复。若看到“后续操作 0”且没有“结果与报告”页签，请从会话中最新的工作面板工具结果点击“在标签页中打开应用”，切换右侧查看器。只点旧面板的刷新会重新读取业务状态，不能替换已缓存的组件程序。“0”是旧版待确认表单数，不等于没有可用操作。

若同时出现“无法加载此回复”或整个应用空白，表示宿主尚未正常载入；此时不能据此判断任务状态，也不应重新创建任务或重复提交确认。

新版面板会保存同一入口的显示类型和所选页签。刷新后，历史工具结果不会再次自动打开并覆盖当前查看器。若宿主没有恢复右侧查看器，点击同一面板的“打开 Dev Bridge 工作面板”即可继续，任务状态不会因此改变。

如果连这个入口也被宿主隐藏，可以明确告诉 GPT：“重新打开原任务工作台，沿用原 Session，不审批或启动运行。”这允许再次调用 `panel_show` 恢复展示；不能为此创建新 Session 或新任务。

v45 在宿主接收面板按钮消息后，会请求恢复原 PiP／全屏展示一次。展示请求失败不改变消息送达记录，也不重发消息。用户在发送过程中主动切换任务或显示方式时，保留用户的新选择。

部署后仍显示旧组件时，可在 ChatGPT 设置 → 插件 → devBridge-test → 刷新工具更新插件描述；面板里的刷新按钮只重读业务数据。必须先确认刷新成功、插件详情里的工具描述已经更新；点击过刷新按钮不等于目录更新成功。官方要求刷新元数据后在新对话中复测，而不是仅刷新旧对话页面。新对话可通过原 aiSessionId 只读恢复原任务，不必创建新的 Core Session 或 Task。若插件更新失败（例如刷新接口 HTTP 500）或回复本身无法加载，需先恢复宿主加载，不能把旧组件当作新版本已生效，也不能通过省略 taskActionGeneration 等身份条件重试。

元数据刷新步骤：[OpenAI 官方连接与测试文档](https://developers.openai.com/plugins/deploy/connect-chatgpt#refresh-metadata)。

## 对比插件工具版本

在 GPT 的插件详情中展开 devBridge-test 应用的工具清单。每个工具说明开头展示 `[DevBridge 工具版本 ID: …]`；这是 ChatGPT 导入时保存的 DevBridge 发布版本。与只读 `bridge_diagnostics` 返回的 `serverVersion` 对比即可判断两端发布版本是否一致。没有该标识说明登记的是加入版本标识之前的旧定义；值不同说明工具定义与当前服务来自不同发布。版本相同只表示发布标识相同，不能替代具体 schema 核验。

GPT 插件设置中的 `asdk_app_v…` 是 ChatGPT 自己生成的登记版本 ID，不是 DevBridge 服务版本；两者不能按字符串直接比较。`businessCatalogSHA256` 当前仅覆盖工具名称集合，也不能用于判断参数 schema 或工具说明是否已刷新。
