# 未知确认提交的安全恢复

日期：2026-10-25。部署版本 `.74`，面板 v42，确认单 v12，schema 132。

## 故障与边界

原任务的延续确认单 `confirm_da4afef0f48c9da63a6ef757b57c1c48` 在 Core 为 PENDING；卡片保存了已发出的原提交，显示「确认结果未知」，只能反复回读。原请求暂无消费回执，不能把查无记录当作未消费证明。外层仍按列表的 PENDING 标为「待确认」，与内部状态冲突。另有间歇宿主读取失败，需分别处理。

用户明确选择修复安全恢复流程，保留原任务与历史。

## 恢复实现

新增 app-only `confirmation_submission_withdraw`，输入沿用完整原提交的闭合 DTO，包括原 requestId、准确意图身份、action、variant 与 selection。MCP 重新计算原参数哈希，不接受客户端的 consumed、outcome、force 等判定字段。

卡片「核对并撤回原请求」由用户显式点击：

1. 先读取准确原请求回执。读取失败则停止；已得到正式结果时按该结果展示。
2. 仍未知且持有完整请求时，Core 核对调用者、原 Session、冻结内容和 variant，再使用现有 `RejectCommit` 写入事务封存原请求。
3. 该事务与 `BeginCommit` 串行：消费先发生则只回读原结果，不运行步骤、不撤销业务；封存先发生则记录持久 `REJECTED_NOT_CONSUMED`，迟到提交沿原 requestId 读取拒绝，不能执行。
4. 只有准确、已记录的未消费回执才能恢复编辑。用户仍须重新确认；本次撤回不批准、启动或创建后继工程对象。

同 requestId 的不同载荷拒绝。重复撤回保持同一回执。撤回响应丢失继续保留原请求，可通过原回执恢复。历史卡片和失去当前资格的卡片不能调用恢复写入。恢复响应不触发确认成功交接钩子。

旧 v11 未知快照可恢复完整请求。外层根据准确本地未知标记展示「结果待核对」，不改写 Core 的 PENDING，不把读取失败当作空列表。
